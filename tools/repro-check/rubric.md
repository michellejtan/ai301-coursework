# Rubric: is this reproduction package ready to post?

Five required checks, one per family. Each merges two (or, for behavior, three) checks that turned out to cover the same ground once the combined rubric made the overlap visible — every condition from both original checks survives, folded into one pass condition per row instead of graded twice. `references/evidence-guide.md` is organized the same way and notes which original checks fed each merge.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record (OS, tool/package version, relevant dependency versions) compared against the issue's stated target version/environment. | The report identifies the relevant environment information (tool version, OS, and similar) whenever that information exists and matters to reproducing the issue — omitting it when it was there to state does not pass. If the stated environment differs from the issue's target (older/newer version, different OS, a substituted or private setup), the report names the difference explicitly rather than presenting the result as confirming the current bug unchanged. *(merges `environment-target-match` + `environment-recorded`)* | required |
| steps-followable | The reproduction steps: the exact commands, config, or input given, read as something a stranger with the same environment could type. | The report gives enough specific information — setup, input, and command — for another person to repeat the test without guessing, reaching the same trigger action the issue describes. No step depends on a resource the reader cannot access (a private repo, an unshared config), and no step stops short of the actual trigger. *(merges `steps-followable` + `steps-complete`)* | required |
| behavior-matches-issue | The reproduction's input/scenario and its own quoted artifact (command output, log excerpt, error text) compared to the issue's stated input, trigger, and symptom. | Pass if either branch holds. (A) Claimed reproduction: the same relevant input and scenario the issue describes is used — small changes are okay only if the report explains why they still test the same behavior — and a real artifact from an actual attempt is quoted (not an assertion alone) showing that same trigger's symptom. (B) Claimed cannot-reproduce: a genuine attempt at the same trigger is shown (the same input/scenario, or an explained substitute) with a quoted artifact from that attempt showing no bug, and the report names what differed from the issue's environment or scenario. Branch B is a full pass on its own — it is not a partial credit note under branch A, and an honest, well-explained cannot-reproduce should never be graded against branch A's "shows the same symptom" language. Fails if: no real artifact is quoted at all, a claimed reproduction shows a different symptom without explaining why it is still the same issue, or a claimed cannot-reproduce shows no real attempt. *(merges `behavior-matches-issue` + `issue-match` + `result-match`)* | required |
| evidence-based | The report's claims and stated conclusion, compared against the commands, inputs, or outputs it actually quotes. | The report provides evidence for its reproduction claims rather than only asserting the issue was confirmed — important claims are backed by shown commands, inputs, or outputs — and its conclusion is sized to that evidence: an evidenced cannot-reproduce that names what differed is a pass, a reproduction backed by its own quoted artifact is a pass. Fails when the report asserts certainty, a root-cause diagnosis, or a guarantee ("verified the race condition," "guaranteed reproducible") that its own quoted artifact does not demonstrate, or generalizes the result to an environment or release it never tested. *(merges `evidence-based` + `honest-outcome`)* | required |
| comms-respects-conventions | The claim comment's (and repro comment's) own text, read against the repo's stated contribution/AI policy (the repo-facts block) and against the issue. | Pass if: (a) any condition the policy states is met — disclosure of the tool and extent of AI assistance when required; silence in the policy requires nothing; (b) the claim comment names a specific detail of this issue and a concrete next step, rather than generic assign-me language; (c) neither comment promises an outcome not yet known (a fix, a timeline, a guarantee of success). No overlapping check existed for this family, so nothing to merge here. | required |

## Verdict rule

Accept only if every required check grades pass. If any required check grades fail or unclear, the verdict is reject. `unclear` counts as `fail`.
